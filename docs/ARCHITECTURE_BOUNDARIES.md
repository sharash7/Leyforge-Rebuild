# Leyforge Architecture Boundaries v0.3

## Leyforge Game
`src/game/` owns Leyforge-specific gameplay, orchestration and player-facing presentation.

## LFE — Leyforge Engine
`src/lfe/` owns reusable runtime infrastructure only after a real Leyforge requirement proves the need.

Reserved families: core, content, voxel, world, worldgen, persistence, entities, simulation, navigation, transactions, networks/logistics, magic primitives, vehicles/vessels, networking, platform and diagnostics.

## Forge-ENG
`src/forge_eng/` owns reusable authoring infrastructure shared by real Forge workspaces: schemas/data, editing transactions, history, validation, references, indexing, import/export, baking, preview, asset processing, variants, migration, batch operations, packaging, simulation/test hooks and AI-assistance integration.

## The Forge
`tools/forge/workspaces/` contains creator-facing workspaces. Every major Forge workspace is represented explicitly in the starter skeleton because each is its own showcase section.

Empty directories reserve ownership and visible future coverage. They do not authorize speculative implementation.

## Canonical Content
`content/` is the canonical data-driven layer consumed by the game/runtime and edited/generated by Forge tools.

Avoid separate game/Forge/runtime copies of the same definition.

## Ownership test
- Leyforge gameplay/presentation -> `src/game/`
- reusable runtime infrastructure -> `src/lfe/`
- reusable authoring infrastructure -> `src/forge_eng/`
- creator-facing workflow/UI -> `tools/forge/`
- canonical data -> `content/`
- visual/audio/media asset -> `assets/`
- test only -> `tests/`

When uncertain, keep code closest to the current feature until reuse is proven.
